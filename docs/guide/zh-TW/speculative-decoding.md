# 推測解碼：MTP 與 n-gram 共同草擬

> **狀態。** 已實作於 `src/model/spec.cpp`（草稿策略）與 `src/model/forward.cpp`（草擬 / 驗證 forward）。
> 環境變數列在[使用參考](usage.md#env)。

**對誰有幫助：** 任何在受記憶體頻寬限制的 GPU 上實作推測解碼的人，特別是帶有遞迴狀態（DeltaNet、Mamba 式層）的混合模型，這類模型的快取無法單純截斷；以及任何需要推測輸出與一般 greedy 輸出*完全相同*、而不只是「等價」的人。

## 1. 為什麼推測是唯一真正的槓桿

一個 27B 4-bit 模型每個 token 要讀取 14.33 GB 的權重。在量測到的 604–626 GB/s 串流上限下，一般 decode（逐 token 生成）的上限約為 38 tok/s，而 WHIRL 的 1-token GEMV 已達到該上限的 97–100%（[kernels.md](kernels.md#gemv)）。但驗證多個 token 的成本幾乎和 decode 一個 token 相同，因為所有列只需讀取一次權重：

| 通過模型的列數（Q4_K_M，R9700） | 時間 |
|---|---|
| 1（一般 decode 步驟） | 27.74 ms |
| 2 | 29.21 ms |
| 3 | 30.22 ms |
| 4 | 30.93 ms |
| 5 | 31.71 ms |
| 8 | 34.79 ms |
| 16 | 39.50 ms |

因此每個被接受的草稿幾乎是免費的。工程問題在於：(a) 產生很可能被接受的草稿，(b) 讓多列驗證盡可能便宜，(c) 讓輸出與一般 decode 產生的結果完全相同。

## 2. MTP：模型自帶的草稿層

Qwen3.8 附帶一層 multi-token-prediction 層（`blk.64`，「nextn」）。給定主幹在位置 t 的隱藏狀態 h 以及位置 t+1 的 token，它預測位置 t+2 的 token：

```
x = eh_proj([ enorm(embed(token)) ; hnorm(h) ])
x = one gated-attention layer + FFN (MoE in Ornith), with its own KV cache
draft = argmax(output_head(norm(x)))            # output head shared with the trunk
```

串接：MTP 層自己經過 head-norm 的輸出被當作下一個草稿步驟的隱藏狀態，因此 k 個草稿需要 k 個 MTP 步驟。在我們的提示詞上，第二個串接草稿的條件接受率為 68–77%。

### 2.1 一個草稿循環

1. MTP 草擬 k 個 token；每個草稿 token **以 kernel 參數**傳給下一步，並且留在 GPU 上（以傳值方式傳遞的 token struct；沒有 `hipMemcpy`——為什麼這裡的同步複製會花掉 5%，見 [windows-hip.md](windows-hip.md#streams)）。
2. 主幹在一次前向傳遞中驗證 k+1 列（k 個草稿 + 它們所接續的 token），保留每一列的 logits 與隱藏狀態。
3. 一個 pick kernel 逐列比較草稿與主幹的 argmax，並寫出接受數、下一個 token 與一個控制字。
4. 主機**每個循環同步一次**，讀取控制字、輸出被接受的 token，並將下一個循環排入佇列。

第一個版本如何從 34 提升到 68.8 tok/s（27B，中文思考提示詞，當時草稿上限為 3）：

| 步驟 | 變更 | tok/s |
|---|---|---|
| 無 MTP | int8 GEMV + 融合 + 常駐裝置的狀態 | 34.2 |
| 1 個草稿 | 草擬 1、驗證 2；接受率 75–82% | 50.7 |
| 2 個串接草稿 | 以 MTP 自己經 head-norm 的輸出作為下一個隱藏狀態 | 55.9 |
| 多 token GEMV 對每個權重單元只解碼一次 | T=4 矩陣乘法 35.7 → 28.6 ms | 58.4 |
| 批次化的驗證 attention | 每個 query 2 次啟動 → 所有 query 共 2 次啟動 | 61.1 |
| 3 個草稿 + Q4_K 草稿 head | 第三份快照；草稿 head 由 Q6_K 輸出 head 產生 | 64.3 |
| 整個循環在 GPU 上串接 | token id 作為 kernel 參數，每循環同步一次 | 68.8 |

## <a id="exact"></a>3. 完全一致的要求

WHIRL 的 MTP 輸出與一般 greedy 輸出**逐位元相同**，適用於每一種草稿數 1–10、有無 n-gram 草稿、單一使用者與並行。這是一道關卡（gate），而不是期許。它要求驗證傳遞中的每一列都必須完全按照 1-token decode 的方式計算：

| 元件 | 讓驗證列等於 decode 列的關鍵 |
|---|---|
| GEMV | 多列 kernel 與 1 列 kernel 共用標準的逐單元浮點順序與歸約樹；int8 WMMA 讓整數部分保持精確（[kernels.md](kernels.md#multirow)） |
| Attention | 分組驗證把每個 query 欄完全按單欄方式計算（關閉 contraction、顯式 fma）（[kernels.md](kernels.md#decode-attn)） |
| DeltaNet 狀態 | 逐列快照，或以相同公式重播（§4） |
| 小矩陣 | 每種權重型別在 n = 1 與 n ≥ 2 時都必須使用*相同*的 kernel 家族（反例見下） |
| EOS 處理 | 被接受的草稿在序列結尾處截斷，讓狀態停在一般 decode 停下的位置（§8） |

為什麼要堅持？因為「等價」無法測試，而且接近平手的情況很常見。早期一次重構讓多 token 內積的順序改變了一個 ulp，驗證 logits 與 decode logits 在最後幾個位元出現差異，接近平手的 token 被翻轉，MTP 輸出就不再與 greedy 相符。有了逐位元相等，MTP 與一般輸出之間的任何差異都是 bug，而 gate `MTP greedy == plain greedy` 會立即抓到。

**一個從模型檔案而非引擎溜過的反例：** Swift-1.5 的某個量化版本把很小的 DeltaNet `ssm_alpha`/`ssm_beta` 矩陣存成 F32。WHIRL 沒有針對 F32 權重的 int8 GEMV：n = 1 使用 f32-activation（啟動值）GEMV，n ≥ 2 使用 f16 GEMM——數值行為不同。三個變體的 MTP 輸出都與一般 greedy 不同，自動草稿策略也退化成 1 個草稿。把這些矩陣重新量化為 Q8_0（它有融合的精確路徑，如 unsloth 的 Q4_K_M）就修好了。引擎端的修正（讓 F32 小矩陣在所有 n 下都走同一個 kernel）已列在待辦清單上。見 [quantization.md](quantization.md#f32-alpha-beta)。

Gate：兩個模型在中文與英文提示詞上的 CLI MTP 對一般解碼；草稿數 1、2、5、10 全部相同；每個循環強制使用 n-gram == 一般解碼；server 與並行變體（[benchmarking.md](benchmarking.md#gates)）。

## <a id="replay"></a>4. 回滾 DeltaNet 狀態：先是快照，後來改為重播

attention 的 KV 快取可以透過忽略超出接受長度的位置來「回滾」。遞迴的 DeltaNet 狀態不行：驗證完 k+1 列後，它已經包含了所有列。

**快照（第一版設計）。** 驗證期間，每一列之後的狀態被寫入快照緩衝區（乒乓式的 `*_alt` 緩衝區，後來改為最多 15 組的陣列）。在第 k 列被拒絕時，引擎把狀態指標換成快照 k——只是指標交換，沒有複製。狀態與快照指標以傳值方式作為 kernel 參數傳入。成本：3 個草稿時每循環約 0.4 ms，但 27B 模型（48 層）每組快照為 150 MiB，而一次 16 列驗證要花約 2.6 ms 寫入它們。server 必須保留 8 組（1.2 GiB）。

**重播（目前設計，server 預設）。** 驗證不再寫入逐列快照，甚至不寫最終狀態。它按 slot 與層記錄每一列的*輸入*：conv 輸入列 `[16][convCh]` 與 delta-rule 輸入 `[16][head][k 128 | v 128 | decay | beta]`（27B 每個 slot 66.3 MiB）。主機判定接受了 a 列之後，為該 slot 標記 `a + 1` 列待處理。下一次驗證的 conv 與 step kernel 會先把待處理列套用到狀態上——使用與驗證內部完全相同的公式，因此結果與快照所保存的逐位元相同——寫入一份新的基準狀態，然後再處理新的列。其他所有讀寫狀態的路徑都會先提交待處理列（prefill（提示詞預填）、單序列前向傳遞、檢查點儲存）或捨棄它們（檢查點載入、重設）。

| 重播的效果 | |
|---|---|
| 四個並行使用者下的 12 列驗證 | 40.42 → 39.47 ms |
| server 用於快照組的 VRAM | 1.2 GiB → 0（當時 KV 池因此增加了 39,424 個 token） |
| server 中每個 slot 的 n-gram 草稿數 | 不再受 8 組快照限制（最多 15） |
| 成本 | MoE 模型，1 個使用者：−0.5%（下一次驗證要多重播約 1.3 列） |

可能的下一步：在第二個 stream 上用一個 kernel 套用所有層與 slot 的待處理列，與下一輪 MTP 草稿步驟重疊執行。

## <a id="auto"></a>5. 自動選擇草稿數

最佳的固定草稿數取決於內容。最大草稿數掃描，27B，tok/s（coding = 5 個任務 × 600 token 的調和平均）：

| 最大草稿數 | Coding，無思考 | Coding，思考 | 中文 | 英文 | 14k 上下文 | 24k 上下文 |
|---|---|---|---|---|---|---|
| 1 | 61.1 | 59.1 | 55.1 | 54.3 | 47.8 | 40.6 |
| 2 | 81.7 | 75.7 | 65.8 | 61.4 | 52.8 | 44.8 |
| 3 | 94.3 | 85.4 | 67.3 | 60.2 | 52.5 | 41.9 |
| 4 | 103.2 | 90.1 | 67.3 | 58.7 | 50.7 | 36.5 |
| 6 | 109.9 | 90.3 | 59.4 | 53.6 | 43.9 | 30.1 |
| 8 | 111.1 | 83.7 | 51.7 | 44.8 | 36.0 | 24.4 |
| 10 | 95.6 | 71.2 | 42.7 | 37.2 | 30.1 | 20.4 |
| **auto（上限 8）** | **105.2** | **90.1** | **67.6** | **60.4** | **52.4** | **44.2** |

程式碼需要 6–8，一般文字 3–4，長上下文 2–3。自動策略是一個成本模型：

- 對每個草稿位置 i，以 EMA 追蹤**條件接受率** p_i（在草稿 1..i−1 已被接受的前提下，草稿 i 被接受的機率）。k 個草稿時每循環的期望 token 數：
  E(k) = 1 + Σ_{j=1..k} Π_{i≤j} p_i。
- 對每個 k 追蹤**量測到的循環時間** T(k)（EMA）。
- 每個循環選擇使 E(k) / T(k) 最大的 k，並加上 3% 遲滯以對抗計時雜訊，且每 32 個循環探測一次相鄰的 k。

它會落在各類內容的最佳值附近。在 8060S 上於單一行程中以交錯提示詞檢查（避免熱漂移）：auto 31.36 tok/s，對比最佳固定草稿數（4）的 31.28。沒有量得到增益而被移除的變體：64 個循環後讓計時表過期、把深位置的接受率往前一位置收縮、跨請求保留接受率。

**MoE 模型：1 個草稿。** Ornith 的逐位置接受率為 92 / 31 / 4 / 0%；3 個草稿時跑 171–172 tok/s，在 24k 時比沒有 MTP 還慢。固定為 1（可覆寫）。

**Server 的特殊處理：**

- 依 decode 中的 slot 數設定草稿上限（dense）：1–4 個 slot 分別為 `{8, 7, 4, 3}`，即最多 16 個驗證列；成本模型在上限內選擇。把 4-slot 的上限從 2 提高到 3（16 列）在四個使用者時帶來 +10%。
- 草稿數為零時（使用者太多），MTP 層仍會處理被接受的 token（不跑草稿 head），讓它的 KV 快取保持完整，草擬可以立刻恢復。
- **當請求在閒置的引擎上開始時，重設計時表。** server 原本跨請求保留循環時間表；單一使用者連續送出請求時，從第二個請求起就拿到過多的草稿（8060S：每循環約 4.5 個草稿，CLI 中約 3.3 個）。在閒置啟動時重設讓請求 2–4 快了 +4.1%，server 相對 CLI 的速度從 −3.6% 變成 −0.5%。
- 逐 slot 的草稿數（把草稿從最不可能被接受的 slot 移到最可能的 slot）在兩個混合使用者時帶來 +13%，但讓低接受率的請求慢了約 10%、固定批次的總耗時慢了 5%；為了公平性維持關閉。

**p-min / n-min（選用，關閉）。** pick kernel 也可以計算草稿的 softmax 機率；在前 n-min 個草稿之後，當機率低於 p-min 時停止草擬。停止判斷在 GPU 上執行（一個停止旗標讓後續的草稿 kernel 立即結束），因此每循環仍只同步一次。搭配自動策略時，p-min 0.3 讓速度變化 ±1%——不設為預設。

## <a id="draft-head"></a>6. 讓草稿更便宜：草稿 head 量化

輸出 head（248,320 × 5120，Q6_K，1.04 GB）每個草稿步驟都要跑一次，因此主導了草稿成本。先量測：**接受率幾乎不受草稿 head 精度影響**（只有 argmax 重要）：在固定 6 個草稿下，完整 Q6_K head 58.8%、Q4_K 59.1%、Q3_K 59.2%。

**D2（每個權重 2.5 bits）。** 每 32 個值一個 f16 scale，每個值一個 2-bit 碼，`w = s · (2c − 3)`，以 structure-of-arrays 方式儲存（每列碼 K/4 bytes + scale K/16 bytes）。在載入時於 GPU 上由 Q6_K head 建立，每個區塊從 6 個候選中選擇平方誤差最小的 scale。有自己的 GEMV（int8 activation、`v_dot4`、1–16 列）。大小從 715 MB（Q4_K head）→ 397 MB，也因此省下 318 MB 的 VRAM。

| 草稿步驟 | 完整 Q6_K head | Q4_K head | D2 head |
|---|---|---|---|
| R9700 | 2.72 ms | 2.17 ms | **1.64 ms** |
| 8060S | 6.88 ms | 5.44 ms | **4.05 ms** |

搭配自動策略的交錯 A/B：R9700 27B +2.4%、MoE +2.0%；8060S +1.5% / +2.5%。（每個草稿的接受率從 63.2% 降到 59.4%，因為策略送出了更多草稿；每秒 token 數上升。）

**Q4_K 的 MTP 區塊。** 把 MTP 層的 Q6_K 矩陣（約 330 MB）重新量化為 Q4_K（約 225 MB）一開始被否決（接受率 −1.5 個百分點，速度 −1.6%）。在其他加速完成後重新量測，它帶來單一使用者 +0.8%，並把四個使用者時每循環的 MTP 時間從 5.00 降到 4.35 ms，因此現在是 dense 模型的預設——這是為什麼核心變快後要重新測試被否決的小點子的一個例子。MTP 區塊以 **Q8_0** 儲存的檔案（Swift-1.5 MXFP4 系列：每個草稿步約 450 MB，外加 2-bit head）也會得到同樣的 Q4_K 副本（`requant_q80_q4k`，約 240 MB）；輸出不變。Swift MXFP4-A、R9700、約 16k token 的 prompt、穩態 decode：單一使用者 78.3 → 85.4 tok/s，四位使用者合計 213.7 → 221.2 tok/s（兩者皆已含 `attn_wsplit2`）。

**被否決的：** Q3_K 草稿 head（接受率不變，但它的 GEMV 只跑到約 488 GB/s：+0.3%）；把草稿詞彙表截斷為前 N 個 token id（中文 token 的 id 很高：接受率從 82% 降到 28–33%；後來以 150,000/100,000 個 id 測試，2.58 → 2.43 tokens/循環）。

模型檔案注意事項：以 Q8_0 儲存的輸出 head 會讓每個草稿步驟都更昂貴。在三個 Swift-1.5 MXFP4 變體中，Q8_0 head 的檔案接受率最高（73.2%），但 MTP 最慢（98.0 tok/s，對比 Q6_K head 檔案的 117.0）。見 [quantization.md](quantization.md#swift)。

## <a id="ngram"></a>7. n-gram 共同草擬

編輯任務（重新命名變數並把檔案寫回、翻譯註解、重構）會複製提示詞中的長段落。在這類段落上，MTP 在其 8 個草稿的上限內已經 100% 被接受；收益來自**更長的草稿**（15）與**更便宜的循環**（n-gram 循環不跑 MTP 草稿步驟：16 列驗證約 43–44 ms，對比 8 個草稿的 MTP 循環約 49 ms）。

### 7.1 第一個版本做錯了什麼

一個未經測試的第一版讓所有編輯提示詞都變慢（編輯 −13%，其他 −5…−7%）：只要有 n-gram 匹配就使用，不管它過去的表現；只取 3-gram 最近一次出現的位置（常見的程式碼 3-gram 如 `;\n    ` 會指向錯誤的地方）；而且上限被限制在 MTP 的 8。調查為什麼複製檔案時 n-gram 草稿只被接受 25%，挖出了兩個不相關、而且影響遠超出 n-gram 草擬的問題：

- **一個 tokenizer bug** 把縮排的程式碼切成非標準的 token；模型寫出的是標準 token，所以 MTP 複製正常，n-gram 查找卻不行（[pitfalls.md](pitfalls.md#tok-1)）。
- **CRLF：** 在提示詞內的 Windows 檔案中，`"\r\n"` 是 token 317；模型寫回的是 LF，token 198。n-gram 索引現在使用 token 層級的 CRLF→LF 正規化表（每個包含 `\r\n` 的 token 都對應到相同文字但使用 LF 的 token；在 5 個原始碼檔案上，全部 653 個 CR token 都 1:1 對應，且正規化後的序列等於對 LF 檔案做 tokenize 的結果）。匹配使用正規化後的序列；草稿輸出 LF token，除非模型自己一直在寫 CR token。

### 7.2 設計

- **索引。** 歷史（提示詞 + 輸出）的每個位置都以一個 3-token 鍵與一個 12-token 鍵插入（hash map；每個鍵串起所有更早的位置）。
- **候選：** 上一個提案來源位置的延續（複製時通常是對的）、12-token 鍵鏈上的前 16 個項目，以及——若最佳匹配短於 12——3-token 鏈的前 16 個。選擇**向後匹配最長**的候選（上限 256，平手 → 最近的），至少 3 個 token。提案長度最多 15 個草稿（16 個驗證列）。
- **對每個提案做反事實評分。** 無論提案是否被採用，事後都會拿它與實際產生的 token 比對評分，所以 n-gram 的逐位置條件接受率永遠是最新的。接受率依匹配長度分成三個桶追蹤（< 8、8–23、≥ 24；先驗 0.35 / 0.7 / 0.85；EMA 0.2）。
- **決策。** 每個循環比較 `max_k E_ng(k) / T_ng(k)` 與 MTP 選定的 E/T，只有在 n-gram 較好時才使用它，並採用最佳的 k。n-gram 循環時間另外量測（量測到之前的先驗：1 個草稿的 MTP 循環 × (1 + 1.5%·(k−1))；某個列數第一次出現時不記錄，因為第一次 16 列驗證帶有一次性約 50 ms 的成本）。n-gram 循環不會更新 MTP 的接受率或計時模型。
- **一個 n-gram 循環**只在待處理列上跑 MTP 層（讓 MTP 的 KV 快取保持完整），並驗證由主機直接提供的 token。
- **n-gram 草稿之後不接 MTP 串接：** MTP 串接需要每個草稿位置的隱藏狀態，而 n-gram 草稿沒有。
- **上限。** CLI：若 VRAM 足夠，會預先配置額外的快照容量，讓 n-gram 能提出 15 個草稿；否則上限等於現有容量（decode 途中不會延遲配置任何東西，也不會有東西溢出到共享記憶體）。Server：每個 slot 的上限 = min(15, 16 / 活躍 slot 數 − 1, 該 slot 已映射的 KV 頁, 上下文)。

## <a id="eos"></a>8. 被接受草稿的序列結尾截斷

當一次驗證接受了多個草稿，而其中一個是 `<|im_end|>`（或 `<|endoftext|>`）時，它之後的草稿（`\n`、`<|im_start|>`、…）以前也會被消耗：可見輸出停在 EOS，但 DeltaNet 狀態與快取的 token 清單已經多前進了 1–3 個 token。下一輪對話會把歷史重新渲染為 `content<|im_end|>\n<|im_start|>user…`，因此生成結束時的檢查點落在共同前綴之外，無法使用。

修正：接受數在 EOS token 之前截斷，並由 EOS 作為選定的 token（驗證在該位置產生的正是這個 token，所以輸出不變，狀態停在一般 decode 停下的位置）。`max_tokens` 也以相同方式截斷（最後輸出的 token 不會再餵回去）。對多輪快取命中的影響見 [kv-and-caching.md](kv-and-caching.md#think-open)。

## <a id="sampling"></a>9. 推測取樣（temperature > 0）

草稿是草稿 head 的 argmax（確定性的）。主幹以取樣分布下的機率 p(draft) 接受一個草稿；被拒絕時，從移除該草稿 token 並重新正規化後的分布中取樣。對確定性草稿而言，這能完全重現目標分布。亂數由 (seed, token index) 推導，因此帶 seed 的請求無論單獨執行、並行執行、MTP 開或關，都會產生相同的文字。

## <a id="vs-llamacpp"></a>10. 為什麼 llama.cpp 的 MTP 在這張卡上比較慢

相同的 GGUF、相同的 R9700、greedy。統一的 server 測試流程（19 個提示詞；llama.cpp b11214 ROCm，參數
`--spec-type draft-mtp --spec-draft-n-max 3 --spec-draft-n-min 0 --spec-draft-p-min 0.3`）：

| Qwen3.8-27B Q4_K_M | llama.cpp | WHIRL |
|---|---|---|
| Decode，無 MTP | 30.9 tok/s | 33.9 |
| Decode，MTP | 56.9 | 105.9 |
| 草稿接受率 | 82.4%（30,100 / 36,528） | 64.8%（33,353 / 51,461） |
| MTP 輸出 == 一般輸出 | 19 個提示詞中 6 個 | 19 個中 19 個 |

（WHIRL 數字來自同一次執行；後來的 kernel 工作把 WHIRL MTP 提升到 110.4。）更早一次兩個引擎都把草稿上限設為 3、在五個 coding 任務上的正面對比：WHIRL 87–94 tok/s，對比 llama.cpp 61–68，接受率幾乎相同（Java 任務：441/483 vs 437/483）。從量測中可以歸因的：

1. **每循環成本。** 在 WHIRL 中，驗證 4 個 token 只比 decode 1 個多約 15%，整個循環在 GPU 上串接、只同步一次，而且草擬使用 2-bit head。在相同接受率下，WHIRL 在相同草稿上限時每秒仍多產生約 40% 的 token。
2. **草稿數。** llama.cpp 在這裡固定最多 3 個草稿；WHIRL 的策略最多使用 8 個（搭配 n-gram 為 15 個），這對程式碼最重要。WHIRL 較低的每草稿接受率是送出更多草稿的預期結果——每循環的 token 數更高。
3. **完全一致性。** llama.cpp 的批次驗證與其單 token 路徑並非逐位元相同（MTP 開啟時 19 個輸出中有 13 個改變）。WHIRL 的自適應策略依賴逐位元相同的驗證，才能在長草稿串時保持正確。
4. **MoE。** 在 Ornith 上，llama.cpp 的 MTP 大致沒有影響，在長上下文時更慢（短提示 decode 99.5 → 101.7 tok/s，24k 時 89.7 → 84.1）；WHIRL：短提示 158.9 → 188.1。

在長上下文時差距縮小（24k：早期比較中 WHIRL 45.1 vs llama.cpp 39.8），因為對兩個引擎而言，attention 都佔了每個循環更大的比例。
